Chaos experiment 5: VRAM exhaustion (hypothesis in chaos-hypotheses.md)

Result: the hypothesis predicted a hard failure (`torch.OutOfMemoryError`,
a crash loop). That did not happen. The first write-up of this
experiment concluded vLLM was simply "more resilient than expected" -
that conclusion did not survive a second look at the numbers (see
"what the first write-up got wrong" below) and has been replaced with
a verified mechanism: on this machine, VRAM exhaustion fails *soft*,
not hard, because of a Windows/WDDM driver behavior that a native
Linux host does not have.

Method: scaled vLLM to 0 replicas (freeing the whole card), started a
scratch Pod (reusing the already-pulled vllm/vllm-openai:v0.28.0 image
- no new image pull - with the same CDI annotation, runtimeClassName,
and baseline security context as the real vLLM Deployment) that
allocates a fixed block of GPU memory with `torch.zeros(..., device=
"cuda")` and holds it, then scaled vLLM back to 1 replica to see
whether it would fit.

=== attempt 1: hog = 512 MiB, held while vLLM was still running ===
Abandoned before testing - deleting vLLM's pod would free its own
~2.6 GiB, more than offsetting a 512 MiB hog on a 4096 MiB card.
Scaled vLLM to 0 instead, to control the free-memory budget directly.

=== attempt 2: hog = 2.3 GiB, vLLM scaled 0 -> 1 ===
nvidia-smi before scale-up: 2435 MiB used (hog only), 1528 MiB free.
vLLM started cleanly (1/1 Ready, 0 restarts) and served a real request
(HTTP 200). nvidia-smi afterward: 3852 MiB used, 111 MiB free.

=== attempt 3: hog = 3.6 GiB, vLLM scaled 0 -> 1 ===
nvidia-smi before scale-up: 196 MiB free. vLLM again started cleanly
and a real generation request (max_tokens=100) returned a complete
100-token response (HTTP 200, request_id b210440d..., duration_ms
3383.4 per the gateway's own audit log). nvidia-smi afterward: 3886
MiB used, 77 MiB free.

=== what the first write-up got wrong ===
The first version of this file concluded vLLM's "real minimum
footprint" was far smaller than its ~2.6 GiB steady-state figure,
because nvidia-smi's "used" total only grew by ~119 MiB between
attempt 2 and attempt 3 (3852 -> 3886) despite vLLM needing to load a
1.40 GiB checkpoint (per its own startup log) plus a fixed 512 MiB
KV-cache reservation. Those two numbers cannot both be true - a model
that size cannot run in under 120 MiB of *additional* dedicated VRAM.
nvidia-smi's "used" figure was not accounting for everything using the
card.

=== the real mechanism, verified ===
Windows' own GPU performance counters (`Get-Counter`) show what
nvidia-smi does not - a second memory pool, "Shared Usage" (host RAM
borrowed by the GPU driver), alongside "Dedicated Usage" (the real
VRAM nvidia-smi reports). Both counters were read for the RTX 3050's
own adapter LUID specifically (`...14d53`); this host also reports an
integrated-GPU adapter under a different LUID, which is not the card
any of this ran on and is excluded below.

  baseline (vLLM serving normally, no hog):
    dedicated = 2,745,901,056 B (~2619 MiB - matches nvidia-smi's own
                2615 MiB steady-state figure used throughout this
                chaos day)
    shared    =    94,633,984 B (~90 MiB)
  (the card with literally nothing running was never separately
  measured in this session - not claimed here)

  hog alone (3.6 GiB allocated, vLLM scaled to 0):
    dedicated = 3,953,840,128 B (~3770 MiB - matches nvidia-smi's 3767 MiB)
    shared    =    79,953,920 B (~76 MiB - essentially unchanged from
                baseline)

  vLLM scaled back up alongside the hog (measured mid-startup and
  again once Ready - identical both times):
    dedicated = 4,082,532,352 B (~3893 MiB - the card, maxed)
    shared    = 2,321,809,408 B (~2214 MiB - up from ~76-90 MiB baseline)

What this establishes: a ~2.2 GiB block of GPU-adapter memory moved
into host RAM at exactly the point vLLM needed more than Dedicated had
left. What it does not establish: whose allocation moved. `GPU Adapter
Memory` counts the whole adapter, not a specific process, and this
host's WSL2 GPU paravirtualization reports GPU activity through a
single VM-level process, not per-container - there is no counter here
that can attribute the moved memory to the hog specifically rather
than to vLLM's own, mostly-untouched 512 MiB KV-cache reservation.

One thing the latency measurement below does establish: vLLM's model
weights did not move to host RAM. Decoding one token at a time reads
the weights on every step: if those ~1.4 GiB of weights had been
served over PCIe instead of the card's own memory, decode would have
been several times slower, not ~10% slower. So whatever moved, it was
not the part of vLLM doing active work on every token - consistent
with (but not proof of) the hog's idle allocation being the one that
got relegated.

Described generically, since the exact in-driver mechanism was not
directly observed: on this host, the Windows graphics driver stack
backs GPU memory overflow with host RAM instead of failing the
allocation outright. Native Linux has no such fallback through this
stack; the same test on bare-metal Linux would plausibly produce the
`torch.OutOfMemoryError` crash loop the hypothesis predicted, though
that was not tested here - no native Linux host was available to this
project. This machine's WSL2/Windows stack was not a neutral test
environment for this specific experiment, and that is itself worth
recording, not smoothing over.

The hypothesis predicted an OOM crash loop, not a latency cliff - no
latency claim was part of the original prediction. The latency numbers
below are reported as a separate, additional observation, not as
confirming or denying the hypothesis itself.

A single cold (cache-miss) request during the hog-holding state
measured 3383.4 ms (per the gateway's own audit log, request_id
b210440d...); a single cold request once the hog was removed measured
3078.4 ms. Each is one sample, not an average, and the two used
different prompt text (a repeated prompt would have hit the response
cache instead of forcing a real generation) - so this is a rough,
one-shot comparison, not a controlled benchmark. The ~10% difference
is at least consistent with vLLM's active working set staying in fast
memory throughout.

=== alerting gap found along the way ===
Prometheus's own retained metrics put the peak `nvidia_smi_memory_used_
bytes / nvidia_smi_memory_total_bytes` ratio during this test at
~95.4% (3910 MiB / 4096 MiB) - right at the edge of what would be
"saturated" by any reasonable definition. No alert fired, because the
only GPU alert that exists, `PalisadeGPUSaturated`, checks
`nvidia_smi_utilization_gpu_ratio` (compute busy-ness) `> 0.95` for 10
minutes - there is no alert on GPU *memory* pressure at all. This
platform would not have paged anyone if this experiment had gone
worse. Noted here as a finding, not yet fixed; a real memory-ratio
alert is a reasonable follow-up, out of scope for this chaos day.

=== recovery ===
Deleting the hog Pod was sufficient every time; nvidia-smi's reported
free memory returned to the exact pre-experiment baseline (2615 MiB
used, 1348 MiB free) with no Docker Desktop restart, no `make gpu-cdi`
re-run, and no host-level GPU reset needed at any point. No pod in the
palisade namespace gained a restart attributable to this experiment;
`PalisadeRestartLoop` never had cause to fire.

Conclusion: the acceptance criterion for this experiment was "capture
what actually happens," not "reproduce a crash." What actually
happened, on this specific host, is a soft degradation mediated by the
Windows graphics driver's own handling of GPU memory overflow, not the
hard OOM the hypothesis predicted - and that distinction matters for
anyone reading this as a production-readiness signal: the resilience
observed here is most plausibly a property of running under this
host's WSL2/Windows driver stack, not of this deployment's own design,
and should not be read as "this configuration tolerates running out of
VRAM" on a native Linux host, which was not tested.
