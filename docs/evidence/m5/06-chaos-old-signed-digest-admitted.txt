Chaos experiment 4b: an old, genuinely-signed M3-era digest is admitted
(hypothesis in chaos-hypotheses.md)

Result: confirmed exactly as hypothesised. Kyverno's signature policy
checks identity and validity, not currency - an older digest that was
really built and signed by ci.yml, before any of M4's features
existed, is let through the same as the current one.

Digest used: sha256:d8a0af80253621922cb9d320691a2ce74a027d6ba5fadc67ff2ea6acfa5b891e
- the exact digest from b444021 (the last gateway bump before c60c80c,
"m4: per-tenant budgets, rate limits, response cache, prompt guard...")
and also the one used as the positive control in M3's own unsigned-
image negative control (docs/evidence/m3/03-unsigned-image-refused.txt)
- so this is a digest independently known to carry a real signature
from this repo's own CI.

The gateway's live rendered Pod spec was pulled from the cluster and
replayed with only the image digest swapped, same discipline as M3's
test (every baseline rule - non-root, drop ALL, read-only root,
resource limits - must pass identically so the signature is the only
variable):

  $ kubectl apply --dry-run=server -f old-m3-pod-full.json
  pod/gateway-old-m3-digest created (server dry run)

No signature-related denial at all on the dry run - Kyverno's
verify-gateway-signature rule passed silently. (An earlier attempt with
a bare, minimal Pod spec was correctly rejected, but by the unrelated
pod-security-baseline policy - missing drop-ALL/read-only-root/non-root/
resource-limits - confirming those are enforced independently of the
signature check and is not evidence about the signature policy itself.)

Then applied for real, to confirm the hypothesis's second half (the
pod actually starts, not just passes admission), and deleted it
immediately after to avoid it taking live Service traffic alongside
the real gateway Deployment (it carries the same gateway labels):

  $ kubectl apply -f old-m3-pod-full.json
  pod/gateway-old-m3-digest created

  $ kubectl wait --for=condition=Ready pod/gateway-old-m3-digest --timeout=60s
  pod/gateway-old-m3-digest condition met

  $ kubectl get pod gateway-old-m3-digest
  NAME                    READY   STATUS    RESTARTS   NODE
  gateway-old-m3-digest   1/1     Running   0          k3d-palisade-server-0

  $ kubectl delete pod gateway-old-m3-digest --wait=true
  pod "gateway-old-m3-digest" deleted from palisade namespace

Together with 4a (docs/evidence/m5/05-*), this fully exercises both
sides of ADR 0008's claim: the policy is identity-exact, not merely
recency-based or "any valid signature passes" - a real signature from
the wrong workflow is refused exactly like no signature; a real
signature from the right workflow is accepted no matter how old.
